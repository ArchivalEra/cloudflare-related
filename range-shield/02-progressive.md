# 02-progressive — 首分片 unblock 与流式拼回（RS3 #23）

> 目标：seek 等待从“全文件就绪”降到“首需分片就绪”。

## 1. 响应流程

```
请求 range [a,b) → 分片序列 [s_k .. s_m]（按客户端字节序排列）
s_k 就绪 → 立刻发响应头（206 + Content-Range）+ s_k 覆盖段字节
s_{k+1}..s_m → 边到边流（chunked），到一片发一片
```

* 头可以先发：状态码与 `Content-Range` 只依赖请求本身，不依赖分片内容。
* 拼回是纯字节拼接（分片边界在 S 倍数处，range 起止只切首尾两片），无转码。

## 2. 取消与复用

| 事件 | 语义 |
|---|---|
| 客户端断连 | 停止向该 waiter 推送；其已触发的 flight 不取消（结果回填缓存，给后来者用） |
| seek 跳变（新 range 到达） | 旧 waiter 标记失效，停止推送；新请求走正常流程（大概率命中旧 flight 正在拉的分片） |
| 首分片超时 | 整体失败（502/504），不等余片；超时值 = 上游拉取超时（见 02-timeouts 思想：idle 语义） |

## 3. 等待上界

* 上界只设在**首分片**：首分片就绪前客户端一字节拿不到，这是唯一值得设超时的点。
* 余分片无独立超时：随上游流 natural 结束；上游断流按 01 flight 失败语义（同窗同失败）处理，已发字节不追回。
* 大文件 seek（如 3GB 尾部）：首分片通常未缓存 → 等一次冷拉分片（秒级，GDrive 单连 7MB/s 下 5MB 段 < 1s），之后全程流式。
